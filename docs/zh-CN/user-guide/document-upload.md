# 上传文档

本指南介绍如何向 ApeRAG 知识库上传文档。ApeRAG 采用**两阶段提交**:先把文件暂存到上传区,用户二次确认后才触发索引构建。这样可以让你一次准备多份文件再统一入库,出错时也便于修正。

URL 和文本导入请看[URL 与文本导入](./content-import.md)。

## 两阶段流程概览

```
┌─────────────┐    Step 1 Upload    ┌──────────────┐    Step 2 Confirm    ┌────────────┐
│  选择文件    │ ──────────────────► │  上传暂存区   │ ──────────────────► │  索引构建   │
│  (本地磁盘)  │                     │  status=     │                      │  (异步)     │
│             │                     │  UPLOADED   │                      │             │
└─────────────┘                     └──────────────┘                      └────────────┘
```

- **Step 1 `upload`**:文件写入 ApeRAG 的对象存储,**未入索引**;状态 `UPLOADED`
- **Step 2 `confirm`**:用户点击"保存到知识库"后,状态转 `PENDING` → `RUNNING`,开始解析 + 分块 + 向量化 + 全文索引 + 知识图谱(按 Collection 配置)

未 confirm 的文档会一直留在暂存区,你可以删除 / 替换 / 追加后再 confirm,不会占用索引配额。

## 支持的文件类型

| 类型 | 扩展名 | 说明 |
|---|---|---|
| PDF | `.pdf` | 推荐;支持图像 + 文字 + 表格(MinerU 解析) |
| Word | `.docx` / `.doc` | 会先转 PDF 再解析 |
| PowerPoint | `.pptx` | 会先转 PDF 再解析 |
| Excel | `.xlsx` | 解析为 Markdown 表格 |
| Markdown | `.md` | 直接处理,保留结构 |
| Text | `.txt` | 纯文本 |
| HTML | `.html` / `.htm` | 抽取正文 |
| 代码 / 其他文本 | `.py` `.java` `.go` 等 | 视为纯文本 |

> **图像与扫描 PDF**:需要开启 vision / OCR 能力(Collection 配置里 `enable_vision`);默认只提取可读字符。

## 文件大小与配额

ApeRAG 有三层限制,命中任一都会被拒绝:

1. **单文件大小**:默认几 MB ~ 几十 MB 级别(具体上限由部署方决定)
2. **每 Collection 文档数配额**:由管理员配置
3. **用户存储配额**:跨所有 Collection 的累计存储上限

超限时前端在暂存区显示具体原因(例如"文件超出大小限制" / "配额已用尽"),你可以删除该文件后换更小的再试,或联系管理员申请扩容。

## 操作流程

### 1. 进入上传页

知识库**文档列表**页 → 右上角"**添加文档**" → 选择"**📁 上传文件**"。

### 2. 选择或拖拽文件

- **单文件选择**:点击"选择文件"按钮
- **批量**:选中多个文件
- **拖拽**:把文件直接拖到上传区(支持文件夹整个拖进来,会递归展开所有文件)

选好文件后**立即开始上传**,每个文件单独进度条。大文件会分块上传(后端由对象存储驱动,用户无感知)。

### 3. 观察暂存区

上传完成的文件进入**暂存区**:

```
┌─────────────────────────────────────────────────────────────┐
│  暂存区(待确认)                                             │
├───────────────────────────────────────┬──────┬─────────────┤
│ 文档名                                 │ 大小 │ 状态        │
├───────────────────────────────────────┼──────┼─────────────┤
│ 📄 user_manual.pdf                    │ 5 MB │ ✅ 已上传    │
│ 📄 api_reference.docx                 │ 3 MB │ ✅ 已上传    │
│ 📄 duplicate_file.pdf                 │ 1 MB │ ⚠ 重复       │
│ 📄 oversized.pdf                      │ 50MB │ ❌ 超过限制   │
└───────────────────────────────────────┴──────┴─────────────┘
                                        [移除]  [保存到知识库]
```

状态说明:

- **✅ 已上传(UPLOADED)**:文件已存入对象存储,等待 confirm
- **⚠ 重复**:该知识库里已有内容完全相同的文档(按 **SHA-256 哈希**判重);确认仍可入库,但建议先移除
- **❌ 失败**:文件未通过校验(超限 / 不支持的类型 / 配额不够 / 网络中断);可移除后重新上传

### 4. 确认入库

点击"**保存到知识库**"。系统会把所有选中文档从 `UPLOADED` 转为 `PENDING`,然后按 Collection 配置的索引类型(向量 / 全文 / 知识图谱 / 摘要 / 视觉)异步开始构建。

页面跳转回文档列表,文档状态随进度更新:`PENDING` → `RUNNING` → `COMPLETE`(或 `FAILED`)。

### 5. 监听处理进度

文档列表页展示每个文档的索引构建状态:

| 状态 | 含义 |
|---|---|
| `UPLOADED` | 已上传暂存,未 confirm |
| `PENDING` | 已 confirm,排队等 worker |
| `RUNNING` | 正在解析 / 分块 / 向量化 / 建索引 |
| `COMPLETE` | 所有启用索引已就绪,可检索 |
| `FAILED` | 某个索引构建失败(鼠标悬停看具体错误) |
| `DELETED` | 用户已删除,逻辑隔离(物理清理由定时任务完成) |

点击文档条目进入**详情页**可以看到单文档的 per-index 状态明细(哪个 index 构建失败 / 完成时间 / chunk 数量)。

## 关键行为

### SHA-256 去重

ApeRAG 对**每份上传文件计算 SHA-256 哈希**,并和该 Collection 内已有文档比对:

- 哈希命中 → 标记"重复",暂存区红字提醒
- 用户可以**忽略提醒强制入库**(有时需要版本管理)
- 也可以在 confirm 前移除

哈希去重仅限**同一 Collection 内**;跨 Collection 不做去重。

### 两阶段的好处

为什么不直接 upload + index 一步到位?

- **批量修正**:大量文件时发现上传错了一份,单独移除比整库补就容易
- **资源预览**:上传仅消耗对象存储写入,不触发 worker;确认前可以先看看哪些成功、哪些失败
- **延后索引**:想先整理文档再批量入库,不必着急触发 worker

### 暂存期没有索引,但**占用存储配额**

`UPLOADED` 状态不会消耗索引配额,**但原始文件已经写入存储**,因此计入用户存储配额。长期不 confirm 的暂存文档建议定期清理。

### 索引构建错误不影响其他索引

每种索引(向量 / 全文 / 知识图谱 / 摘要 / 视觉)各自独立构建:

- 向量索引失败不影响全文索引
- 知识图谱失败不影响向量索引
- 系统会**每种都尽力构建**,最后呈现 per-index 状态

文档详情页展示每种索引的状态;单独索引失败可以在文档详情页或管理界面触发**重建**。

### Word / PPT 的 PDF 中转

Word / PowerPoint 文件不是直接解析 `.docx` 内部 XML,而是**先转成 PDF 再走 PDF 管线**。原因:

- PDF 解析管线(MinerU)对布局 / 图片 / 表格的支持远强于 docx 直接读取
- 跨语言 / 复杂样式文档转 PDF 后质量更稳

副作用:`.docx` 的原始格式 metadata(批注 / 修订记录 / 链接 mapping)会在 PDF 转换阶段被扁平化,无法完整保留。若需精确保留,建议先自己转 PDF 或直接用 Markdown。

## 常见问题

### 上传卡在 `PENDING` 很久怎么办?

- 正常情况:`PENDING` → `RUNNING` 延迟 < 30 秒(等 Celery worker 拉取任务)
- 如果超过 5 分钟没进入 `RUNNING`:worker 没运行或被其他大任务 block,联系管理员看 Celery 日志
- 单文档从 `RUNNING` 到 `COMPLETE` 时间随文件大小不同:
  - 几页 PDF:< 1 分钟
  - 几十页 PDF + 向量化 + 图谱:几分钟
  - 上百页大文件 + 启用 vision:可能 10 分钟 +

### 上传失败能否看到具体错误?

暂存区每个失败的文档条目会显示短错误。完整错误栈在文档详情页 → 处理日志 tab 里。

### 已 confirm 的文档能反悔吗?

可以**删除**(软删除,状态转 `DELETED`),索引资源会被异步清理。但 confirm 触发的 worker 任务**已消耗了 API / vector DB 的 write quota**,无法退还。

### 一次上传很多文件会超时吗?

- **上传阶段**:每个文件独立 HTTP 请求,不会互相 block;前端并发上传(默认 3-5 并发)
- **Confirm 阶段**:后端一次性把所有选中文档标 `PENDING`,耗时 < 1 秒;不会超时
- **Worker 阶段**:多文档并行处理(受 worker 数量限制);不影响用户

### 支持文件夹上传吗?

**Web 界面支持拖拽整个文件夹** — 浏览器会递归展开所有文件后逐一上传。但不保留原文件夹结构(所有文件进同一 Collection 的扁平列表)。

若需保留目录层级用于导航/分类,建议用**子知识库**(按目录拆 Collection)或在文档名里加层级前缀。

### 图片 / 扫描 PDF 的文字怎么提取?

需要在创建 Collection 时或编辑 Collection 配置里**开启 Vision**(`enable_vision: true`)。开启后:

- 扫描 PDF / 图片文件走**视觉模型**(通常是多模态 LLM)做 OCR + 理解
- 构建的 `vision_index` 记录每张图对应的文字描述
- 对话时 LLM 可以引用图片原文

Vision 会显著增加 LLM 调用成本,请按需开启。

### 上传同一文件到不同 Collection 会重复占用存储吗?

是。**跨 Collection 的同名文件各自存一份**,不做 cross-collection 去重(SHA-256 去重仅在同一 Collection 内生效)。

如果需要跨 Collection 共享内容,建议用 **Marketplace 分享**(一个 Collection 被多个用户订阅,物理存储只一份)。
